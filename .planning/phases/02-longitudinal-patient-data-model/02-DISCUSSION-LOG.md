## Area 1: Deduplication Strictness

**Question presented:** How aggressive should dedup be? What counts as a duplicate lab value? What does 'flag for review' mean in practice — log-only or a future review queue?

**User decision (verbatim):**
> For observations (labs), only deduplicate when user_id + normalized analyte + observed date clearly represent the same measurement. If there are conflicting values or units for the same analyte/date, do not merge automatically. Instead, store both and flag with a needs_review indicator. For conditions, medications, and allergies: Use normalized canonical names with upsert semantics (latest document updates existing entry).

## Area 2: Promotion Failure Behavior

**Question presented:** If inserting into patient tables fails, does it block the upload (hard fail) or silently log and continue — like the Phase 1 text_extraction_meta pattern?

**User decision (verbatim):**
> Use soft-fail. If promotion to patient tables fails, do not block document upload. Persist the document and structured_result normally. Log the failure with document_id and error details. Promotion must be retryable and idempotent.

**Captured as:** D-04, D-05, D-06, D-07

## Area 3: Conditions & Medications Schema

**Question presented:** ClinicalNote gives free-text strings for diagnoses/medications. How much normalization at promotion time — store raw strings, or clean/structure them further?

**User decision (verbatim):**
> Use a semi-structured approach. Store both raw and normalized values: raw string as extracted, normalized canonical value when possible. Include key fields such as: clinical_status, verification_status (conditions); dose, route, frequency, status (medications). Do not attempt full ontology mapping in v1.

**Captured as:** D-08 through D-13

## Area 4: analyte_aliases Scope

**Question presented:** How many Portuguese→canonical lab name mappings to pre-seed, and is this a static hardcoded list or a Supabase table that grows over time?

**User decision (verbatim):**
> Use a Supabase table, not hardcoded. Seed it with common Brazilian lab terms (Hb, HbA1c, glicose, creatinina, etc.). Allow it to grow over time. Do not implement full LOINC mapping in v1.
